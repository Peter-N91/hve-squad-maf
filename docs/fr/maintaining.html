Préserver la fidélité aux contrats

Maintenir l’adaptateur.
Préserver la méthode.

Les contributions doivent renforcer le comportement natif sans inventer de preuves d’exécution, affaiblir les validations humaines ni dupliquer le contenu des prompts amont.

Une contribution utile commence par un périmètre reproductible.

  1. Décrire le comportement réel

    Ouvrez une issue ou une pull request en indiquant le comportement attendu et le comportement observé, la version de la bibliothèque, la version publiée ou le commit des artefacts, le profil sélectionné et une reproduction minimale. Masquez les identifiants, le contenu privé du projet, les réponses du fournisseur et les données personnelles.

  2. Modifier l’adaptateur, pas une deuxième copie de HVE Squad

    Conservez les chartes, les compétences et les instructions dans leurs projets amont. Les modifications ici doivent acquérir et interpréter les contrats publiés, implémenter les mécanismes natifs de l’hôte ou améliorer les tests et la documentation. Une nouvelle capacité nécessite une implémentation réelle, pas seulement du texte de prompt.

  3. Démontrer les parcours de réussite comme de refus

    Utilisez des tests IChatClient à réponses scriptées pour obtenir un comportement déterministe. Incluez, lorsque c’est pertinent, le refus, les entrées sans réponse, les rôles absents de l’équipe, les preuves modifiées, l’exécution interrompue et l’état invalide. Distinguez les évaluations avec un modèle réel des tests de contrat.

  4. Faciliter la revue

    Gardez la modification ciblée, mettez à jour la documentation et les exemples exécutables concernés, et expliquez les conséquences sur la compatibilité ou l’état. N’incluez pas de packages générés, d’identifiants ni d’état client dans une pull request. Pour les constats sensibles, utilisez le mécanisme privé de signalement de sécurité du dépôt, s’il existe, plutôt que de publier des détails exploitables dans une issue.

Le dépôt utilise les analyseurs .NET et traite les avertissements comme des erreurs. Préservez ce socle et évitez les suppressions qui ne font que masquer des contrats non respectés.

Compiler, tester et empaqueter en local

PowerShell · Vérifications de développement standard
Set-Location C:\Solutions\hve-squad-maf
dotnet restore HveSquad.AgentFramework.slnx
dotnet build HveSquad.AgentFramework.slnx --configuration Release
dotnet test HveSquad.AgentFramework.slnx --configuration Release
dotnet pack src\HveSquad.AgentFramework --configuration Release --output artifacts

La commande d’empaquetage produit artifacts\HveSquad.AgentFramework.0.1.0-preview.1.nupkg à la version de préversion actuelle. Elle ne publie rien. Validez à la fois la référence au projet et le parcours de consommation via le flux de packages local avant de modifier l’empaquetage.

Tester les véritables contrats publiés

Installez Git et APM 0.18.0, puis exécutez la catégorie de compatibilité des versions. Ces vérifications utilisent un modèle à réponses scriptées plutôt qu’une inférence payante, mais nécessitent un accès réseau pour acquérir la version.

PowerShell · Version connue, puis dernière version stable
$env:HVE_SQUAD_RELEASE_VERSION = "v0.16.2"
$env:HVE_SQUAD_REQUIRE_RELEASE_TESTS = "true"
dotnet test tests\HveSquad.AgentFramework.Tests `
  --configuration Release --filter Category=ReleaseCompatibility

$env:HVE_SQUAD_RELEASE_VERSION = "latest"
dotnet test tests\HveSquad.AgentFramework.Tests `
  --configuration Release --filter Category=ReleaseCompatibility

Remove-Item Env:\HVE_SQUAD_RELEASE_VERSION
Remove-Item Env:\HVE_SQUAD_REQUIRE_RELEASE_TESTS

Pour une arborescence d’artefacts déjà installée, utilisez HVE_SQUAD_RELEASE_ROOT pointant vers le répertoire contenant .github et .agents. Supprimez les sélecteurs incompatibles lorsque vous changez de mode de test. La réussite d’une suite de tests de contrat n’atteste ni la qualité d’un modèle réel, ni celle de tous les adaptateurs de fournisseurs, ni la sûreté d’un déploiement, ni une parité complète avec Copilot.

Deux flux de mises à jour indépendants

L’intégration native

Examinez les changements de .NET, de MAF, de Microsoft.Extensions.AI et des autres packages NuGet. Mettez à jour les versions liées de façon cohérente et effectuez la compilation, les tests, l’inspection de l’exemple et les vérifications d’empaquetage local.

Les modifications des options, des effets, des preuves, de l’état ou des statuts de résultat nécessitent une documentation correspondante et des tests de compatibilité explicites.

La méthodologie amont

La source par défaut résout la dernière version stable publiée de HVE Squad. Le commit exact de son étiquette est installé avec le graphe de dépendances correspondant.

Une version plus récente peut modifier les formats ou les contrats de sécurité. Une acquisition automatique n’équivaut pas à une compatibilité comportementale automatique. Un échec nécessite une maintenance de l’adaptateur, pas un repli sur main.

  • Conservez le test de la version connue comme fonctionnelle et celui de la dernière version stable. Ne changez la version épinglée connue qu’après avoir examiné le nouveau contrat et testé le comportement des profils default et full.
  • Ne mettez pas à niveau silencieusement la conversation native d’un projet existant. Conservez sa version, son empreinte et sa composition d’équipe d’origine, ou concevez une migration explicite ayant fait l’objet d’une revue.
  • Examinez les pull requests Dependabot pour GitHub Actions et NuGet. Les propositions de mise à jour planifiées n’impliquent ni fusion automatique ni autorisation de publication de version.
  • Gardez les actions tierces épinglées sur des SHA de commit examinés et maîtrisez les versions des outils. Examinez séparément les changements d’autorisations, les nouveaux accès sortants et la publication des sorties.
  • Mettez à jour cette documentation lorsque les noms du catalogue, la sémantique des sources, les fonctions de rappel, les règles d’effets, les options de l’exemple ou les noms des workflows changent.

La configuration du dépôt reste une action humaine

  • Autorisez les actions prévues et vérifiez que les contrôles requis se terminent avant de les ajouter à la protection des branches ou aux ensembles de règles. Le YAML des workflows n’active pas ces ensembles de règles.
  • Activez les fonctionnalités de graphe des dépendances et d’analyse de code lorsque la visibilité et l’offre du dépôt le permettent. CodeQL dispose de son propre parcours d’analyse et de téléversement.
  • Activez la détection de secrets et la protection des push de GitHub lorsqu’elles sont disponibles. L’analyse des secrets de Checkov complète ces fonctionnalités du dépôt ; elle ne les active ni ne les remplace.
  • Checkov et Zizmor conservent toujours les rapports d’analyse. Le téléversement de leurs résultats vers l’analyse de code s’active explicitement au moyen de la variable Actions du dépôt SECURITY_SARIF_UPLOAD=true pour les exécutions de confiance sur main. Examinez la disponibilité et la politique de publication avant de l’activer.
  • Examinez les problèmes détectés et les erreurs d’exécution des analyses. Une vérification supprimée, un flux manquant ou un analyseur en échec ne doit pas être présenté comme un résultat sans problème.
  • Ne publiez pas de badges de score publics et n’annoncez pas de score sans une véritable politique de publication configurée et une évaluation observée.

Publier une version sur NuGet.org

Cette procédure s’adresse aux responsables de maintenance qui souhaitent rendre la bibliothèque disponible à d’autres développeurs d’applications. Préversion ne signifie pas code source uniquement : une préversion comme 0.1.0-preview.1 peut être publiée sur NuGet.org et installée en spécifiant sa version exacte. Elle reste marquée comme préversion jusqu’à la publication intentionnelle d’une version stable.

État actuel : le dépôt GitHub public existe, mais aucun package NuGet n’a été publié dans le cadre de ce travail. Les étapes ci-dessous nécessitent le compte d’un responsable de maintenance, une autorisation et une action explicite de publication. dotnet pack, git push, une publication de version GitHub et un déploiement Pages ne publient pas de package NuGet.

Séquence de publication

  • Compte et propriété
  • Choisir une version
  • Créer le package exact
  • Téléverser ou pousser
  • Installation par les consommateurs
  • Automatiser ultérieurement

1. Définir le propriétaire du package

  1. Créez un compte NuGet.org ou connectez-vous à un compte existant. Être propriétaire du dépôt GitHub ne confère pas la propriété sur NuGet.
  2. Vérifiez si HveSquad.AgentFramework est disponible ou appartient déjà à votre compte ou à votre organisation. Ne supposez pas qu’un identifiant de package est réservé parce qu’un fichier de projet porte ce nom. S’il appartient à un autre propriétaire, réglez la question de la propriété ou choisissez un autre identifiant avant de publier.
  3. Pour un package appartenant à une équipe, choisissez l’organisation NuGet prévue et ajoutez les propriétaires appropriés. Vérifiez qui peut publier de nouvelles versions. Le champ de métadonnées Authors n’est pas la liste de contrôle d’accès.

2. Choisir la version de l’intégration, pas celle des artefacts HVE

Pour la première publication, conservez 0.1.0-preview.1 si cette version est toujours inutilisée et représente fidèlement le candidat. Pour la publication suivante, attribuez une nouvelle version inutilisée dans le fichier de projet, mettez à jour les notes de version et la documentation, puis examinez et validez ces modifications dans un commit. Un couple identifiant de package/version déjà publié ne peut être ni écrasé ni réutilisé. Une nouvelle version des artefacts amont ne publie pas automatiquement une nouvelle version de la bibliothèque.

Avant l’empaquetage, examinez l’identifiant du package, sa description, ses auteurs, sa licence, l’URL du dépôt, le rendu du README et le contrat d’exécution pris en charge. Utilisez des URL publiques absolues pour les ressources ou liens du README qui ne s’affichent pas dans l’aperçu NuGet. Testez le package via le parcours consommateur avec flux local. N’incluez dans le package ni identifiants, ni données de dossiers, ni rapports de compilation, ni artefacts amont acquis.

3. Construire et identifier le candidat exact

Travaillez à partir d’une copie de travail de l’intégration propre et ayant fait l’objet d’une revue. Les commandes lisent la version effective de la bibliothèque, plutôt que de pousser accidentellement tous les packages restés dans artifacts. Exécutez intégralement les commandes de compatibilité avec la version connue et la dernière version stable ci-dessus avant de publier ; vérifiez les workflows de sécurité pour le même commit.

PowerShell · Préparer un seul candidat de publication versionné, sans publication
Set-Location C:\Solutions\hve-squad-maf
$ErrorActionPreference = "Stop"
$project = "src\HveSquad.AgentFramework\HveSquad.AgentFramework.csproj"
$changes = git status --porcelain
if ($LASTEXITCODE -ne 0 -or $changes) {
    throw "Prepare a clean, reviewed commit before packaging for publication."
}
$commit = git rev-parse HEAD
if ($LASTEXITCODE -ne 0) { throw "Cannot resolve the release commit." }
$version = (dotnet msbuild $project -nologo -getProperty:Version).Trim()
if ($LASTEXITCODE -ne 0 -or [string]::IsNullOrWhiteSpace($version)) {
    throw "Cannot resolve the NuGet package version."
}
$output = Join-Path $PWD "artifacts\$version"
if (Test-Path -LiteralPath $output) {
    throw "Candidate output already exists. Inspect it before deliberately rebuilding."
}

dotnet test HveSquad.AgentFramework.slnx --configuration Release --nologo
if ($LASTEXITCODE -ne 0) { throw "Build or tests failed." }
dotnet pack $project --configuration Release --output $output `
    -p:ContinuousIntegrationBuild=true -p:RepositoryCommit=$commit
if ($LASTEXITCODE -ne 0) { throw "Package creation failed." }

$package = Join-Path $output "HveSquad.AgentFramework.$version.nupkg"
if (-not (Test-Path -LiteralPath $package)) { throw "Expected package is missing." }
Get-Item -LiteralPath $package | Select-Object Name, Length
Get-FileHash -LiteralPath $package -Algorithm SHA256

Conservez le commit, la version et le SHA-256 du candidat pour le dossier de publication. Examinez le manifeste et les fichiers du package, puis installez ce candidat dans une application consommatrice distincte. Si vous avez changé l’identifiant du package, mettez à jour le nom de fichier attendu et toutes les commandes destinées aux consommateurs en conséquence. Ne publiez pas un ancien package du répertoire racine au seul motif que son nom semble correct.

4. Publier via le portail ou la CLI

Par le portail, adapté à une première publication : ouvrez la page de téléversement NuGet.org, choisissez le fichier .nupkg exact du candidat, examinez la propriété, les métadonnées, les dépendances et l’aperçu du README, puis sélectionnez Soumettre uniquement lorsque vous êtes prêt à publier. Aucune clé API n’est nécessaire dans votre terminal. Le portail permet aussi de téléverser les versions ultérieures d’un package dont vous êtes propriétaire.

Par la CLI : créez une clé API NuGet à courte durée de validité, limitée à HveSquad.AgentFramework. La première publication nécessite l’autorisation de pousser un nouveau package ; les clés ultérieures doivent se limiter à pousser de nouvelles versions de ce package. Faites injecter NUGET_API_KEY dans ce processus par un gestionnaire de secrets, sans l’afficher, l’écrire dans le code source ni saisir sa valeur dans l’historique de l’interpréteur de commandes.

La procédure suivante utilise la prise en charge des variables d’environnement de NuGet 7.6 / du SDK .NET 10.0.300 ou ultérieur, ce qui évite de placer une clé API dans les arguments de la ligne de commande. Elle utilise $package issu de l’étape de préparation dans la même session PowerShell. Les utilisateurs de SDK plus anciens doivent utiliser le portail ou mettre à niveau leur SDK, et non ajouter un identifiant secret en clair à la commande.

PowerShell · Publication publique explicite, à exécuter uniquement après validation
if ([string]::IsNullOrWhiteSpace($env:NUGET_API_KEY)) {
    throw "Provision a package-scoped NUGET_API_KEY securely before publication."
}
if (-not $package -or -not (Test-Path -LiteralPath $package)) {
    throw "Prepare and verify the exact candidate package first."
}
try {
    dotnet nuget push $package --source https://api.nuget.org/v3/index.json
    if ($LASTEXITCODE -ne 0) { throw "NuGet rejected the publication." }
}
finally {
    Remove-Item Env:\NUGET_API_KEY -ErrorAction SilentlyContinue
}

Aucun caractère générique ni --skip-duplicate n’est utilisé : un conflit ne prouve pas que ce candidat a été publié. Si une version existe déjà, examinez-la et choisissez une nouvelle version pour des octets différents. Retirer une mauvaise version de la liste publique ne rend pas son numéro de version réutilisable.

5. Vérifier la disponibilité, puis fournir la commande du package aux consommateurs

Attendez la validation et l’indexation NuGet. Vérifiez le statut du package dans la gestion des packages et sa page propre à la version ; utilisez un nouveau projet consommateur pour restaurer la version exacte depuis NuGet.org sans le flux local du candidat. Un échec de validation du package ou un délai d’indexation ne justifie pas d’annoncer une réussite. Une fois 0.1.0-preview.1 réellement publiée et validée, le parcours consommateur devient :

PowerShell · Installation par un consommateur une fois la version disponible sur NuGet.org
dotnet add C:\apps\BidPortal\BidPortal.csproj package HveSquad.AgentFramework `
    --version 0.1.0-preview.1 --source https://api.nuget.org/v3/index.json

Remplacez le chemin d’application et la version de l’exemple par les valeurs réelles. Les consommateurs utilisent ensuite AddHveSquad ou SquadRuntime.CreateAsync dans leur application .NET/MAF existante ; ils n’ont plus besoin de cloner ce dépôt d’intégration. Ils fournissent toujours un client de modèle compatible, des fonctions de rappel de l’hôte et un stockage des dossiers, ainsi que Git/APM pendant l’acquisition des artefacts amont ou une arborescence complète d’artefacts explicitement provisionnée. Aucun plugin Copilot, abonnement Copilot ou serveur HVE Squad MCP distinct n’est requis.

Après une publication réussie, mettez à jour le site et le README pour distinguer une préversion publiée d’une préversion non publiée. Consignez la version NuGet, le commit source et la version des artefacts HVE testée dans les notes de version. Une étiquette ou une publication de version GitHub constitue un élément de provenance utile, mais ne remplace jamais la vérification sur NuGet.

6. Automatisation facultative avec la publication de confiance

La procédure manuelle ci-dessus fonctionne sans ajouter de workflow de publication. Pour une publication CI reproductible, la publication de confiance NuGet peut échanger une identité OIDC GitHub contre une clé API de courte durée. Aucun workflow de publication n’est installé par cette modification de documentation. Un futur publish-nuget.yml devra être examiné avant d’autoriser son écriture externe.

  3. Construisez et validez le candidat exact dans un job sans privilèges. Après la validation de l’environnement, accordez uniquement au job de publication id-token: write et les autorisations nécessaires pour récupérer ce candidat.

Conservez le déploiement Pages, l’acquisition des artefacts et la publication NuGet comme des opérations distinctes.

Activer et maintenir GitHub Pages

  1. Examiner le contenu public

    Le site se compose des fichiers docs\*.html de premier niveau, des ressources partagées de docs\assets et de .nojekyll. Il n’a ni dépendances de compilation, ni polices externes, ni CDN, ni analyse d’audience, ni identifiants d’exécution. Excluez du contenu publié les données de projet, les rapports et l’état natif.

  2. Activer la publication dans GitHub

    Dans le dépôt, ouvrez Paramètres → Pages → Compilation et déploiement et définissez Source : GitHub Actions. Examinez l’environnement github-pages et ses protections de déploiement. Le simple ajout de fichiers de workflow n’active pas ces paramètres.

  3. Exécuter le workflow Pages depuis main

    docs.yml prépare uniquement les fichiers HTML de premier niveau et les ressources autorisées, crée un artefact Pages statique et le déploie. L’étape configure-pages suppose que Pages est déjà activé. Examinez l’exécution et utilisez son URL de déploiement réelle.

  4. Vérifier le déploiement sous le chemin du projet

    L’URL attendue du projet, une fois Pages activé et le déploiement réussi, est https://peter-n91.github.io/hve-squad-maf/. Il s’agit d’une URL attendue, pas d’une affirmation selon laquelle le site serait déjà en ligne. Les liens relatifs maintiennent le fonctionnement de la navigation et des ressources sous /hve-squad-maf/.

Liste de vérification des modifications de documentation

  • Maintenez ensemble les sept pages et la navigation commune. Marquez uniquement la page courante avec aria-current="page".
  • Utilisez des liens locaux relatifs tels que assets/site.css, pas des chemins racine tels que /assets/site.css.
  • Vérifiez les thèmes clair et sombre, la navigation au clavier, le menu mobile, le lien d’accès direct au contenu, le retour de copie, le débordement du code et la structure des titres. Toute la lecture et la navigation doivent rester disponibles sans JavaScript.
  • Conservez le logo communautaire d’origine et la mention de non-affiliation. Il s’agit d’une variante MAF inspirée de la même famille visuelle, pas d’une marque officielle de Microsoft ni d’une approbation de sa part.
  • Comparez les commandes copiables et les exemples d’API à l’exemple d’application et au code source. Distinguez les conceptions futures des fonctionnalités implémentées.
  • Testez chaque page et chaque ancre locale avant le déploiement. Aucun générateur de site basé sur Node ni aucune installation de package n’est nécessaire pour ces fichiers statiques.
