01 / Understand before editing

Modernize a legacy application

A team wants to upgrade a framework without asking an agent to rewrite the entire application in one turn. Use a focused planning request to establish compatibility risks, phase boundaries, acceptance criteria, and prerequisites.

Example request · Planning, not implementation
Research this repository's framework and dependency constraints.
Plan a phased modernization with separate phase details and acceptance criteria.
Identify unknowns and ask me before assuming them.
Stop after planning. Do not edit source or claim tests ran.

Set it up

Start with full if council or supplied input artifacts are needed. modernization is a released specialization, but it does not include every council seat or intake-validator.

Supply the real checkout and a tool-capable IChatClient. Add external retrieval only through an approved ExternalRead host tool.

Know the outcome

Expect PlanCompleted with verified plan and phase-details, or an explicit blocker. A later, separately approved delivery turn can target one bounded code change.

Code edits need a registered writer and output evidence. Compilation and test execution need actual host executors; a model-written checklist is not a test result.

Why native MAF? Keep the company's model choice, logging, authentication, and developer-tool integrations in the application while using a consistent released research/plan/review method.

02 / Plan, approve, attest

Make IaC changes evidence-gated

Use an approved architecture and a narrow infrastructure change as the inputs. Select one producing role per turn: writing IaC and applying it are distinct responsibilities, not an implied combined operation.

Example request · One IaC-producing owner
Use the supplied architecture and constraints to plan one bounded IaC change.
Use iac-author as the single producing owner.
Require council review and explicit implementation approval.
Write only through the registered host tool. Do not deploy.
Review the output against the approved plan and report unresolved blockers.
  1. IntakeExisting architecture inputs
  2. Research + planSeparate phase details
  3. Council + humanConditions must be honored
  4. Produce + reviewReal output evidence

Configure Profile = "full", real project-relative InputPaths, and RequireCouncil = true. Register a role-authorized ProjectWrite tool whose OutputEvidence returns the successfully written IaC paths. The azure profile alone is not a guarantee that all council seats are present.

Deployment is a separate host integration and turn. If you later choose a deployer owner, the host must supply the actual external executor, its least-privilege credentials, exact human approval, and a successful operation receipt. Dry-run evidence must never attest an applied deployment. The library provides no Azure service, shell, or deployment engine.

Why native MAF? Your application can keep resource authorization and change-management controls around every call instead of granting broad shell access to satisfy an infrastructure prompt.

03 / Evidence before a roadmap

Research and plan a product decision

Start from existing interview notes or requirements. Ask for a focused plan, then choose one substantive output owner for any later delivery. This is not the unsupported discovery-interview mode.

Example request · Input-backed product plan
Review the supplied interview notes and requirements as inputs.
Identify evidence gaps, ask unresolved questions, and plan a bounded validation study.
Include phase details and acceptance criteria. Stop after planning.
Do not create backlog items or claim new interviews were conducted.

Dependencies

The product profile includes intake-validator and product specialists. Use full if the request needs all council roles. Provide existing notes as InputPaths; the plan workflow runs intake before planning.

Limits

No automatic BRD + backlog + design + deck + notebook fan-out. Split deliverables into separate owner-specific turns. Backlog writes require a real external host tool; decks require a registered renderer and actual .pptx evidence.

Why native MAF? Put the research/planning experience in an existing product portal without forking the released HVE role instructions or pretending that a report created tracker items.

04 / Your platform, your model

Embed a governed team in an enterprise app

Reuse an existing IChatClient, application identity, approval UI, and auditing pipeline. The library is an in-process integration, not a requirement to introduce another managed agent service.

C# · Host-owned per-role model binding
options.ModelSelector = (role, charter) =>
    role?.Role == "researcher"
        ? new SquadModelSelection(researchClient, researchModelId)
        : new SquadModelSelection(defaultClient, defaultModelId);
options.EnableOpenTelemetry = true;

The clients and model IDs in this snippet are existing host configuration, not bundled providers. A null role identifies the user-invoked coordinator. Use actual model IDs if known; model tiers are only catalog metadata. The host retains the clients' lifetimes.

Keep one active project owner, correlate real human answers, set explicit budgets, and isolate tenant resources in every registered tool. Persist project state and retain its release binding. See the suggested service design before adding remote UI or workers.

Why native MAF? Preserve model choice and enterprise platform ownership while adding methodological gates. This is not evidence that every model provider, compliance control, or deployment topology has been validated.

05 / A second look, not a second build

Review existing artifacts

When an artifact already exists, provide it explicitly and ask for focused review. The runtime must not invent a target or label a review as a new end-to-end delivery.

C# · Configure existing targets before CreateAsync
options.InputPaths = ["docs/design-spec.md", "src/Example.cs"];

// After creating the runtime with these options:
var result = await squad.RunAsync(
    "Review only the supplied existing targets for consistency and unresolved issues. " +
    "Do not implement or deploy anything.",
    cancellationToken);

The paths are examples and must already exist in the selected project. Focused review goes directly to the tester role; no new intake/research/production stages are implied. default includes this role. If council is required, choose a planning workflow instead of trying to bypass it through review-only scope.

Expect ReviewCompleted only when the focused review completes with verified evidence and no blocking outcome. It is not proof that tests ran, the entire system is secure, or a release is ready. Additional validation needs real host functions or your existing engineering process.

When a simpler integration is enough

For a one-shot chat response without persistent methodology, role ownership, approval gates, or output verification, a direct MAF agent may be simpler. Choose the squad runtime when those contracts are worth enforcing. Do not choose it expecting autonomous multi-squad delivery: that scope is not implemented.
